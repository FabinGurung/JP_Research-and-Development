Research

From fragmented AEC records to a reusable relational backbone

The study investigates whether normalized shared data can connect selected design, analysis, estimation and construction-documentation workflows in Nepal.

Prototype-based researchControlled two-span test

Problem

Repeated data, weak traceability, disconnected tools

In the Nepalese AEC sector, building project information is commonly distributed across multiple disconnected documents and software tools. Architectural drawings, structural calculations, quantity estimates, method statements, specifications, and site records are often prepared by different professionals using different formats. This fragmented system makes it difficult to maintain consistency across the complete project lifecycle. A major problem arises when the same information is required in several project stages. A member dimension may be used in architectural layout, structural analysis, quantity calculation, and construction documentation. In a manual workflow, this dimension is often copied from one document to another. If the design changes, each copy must be updated separately. This creates a high possibility of mismatch between drawings, calculations, quantities, and site documents. The lack of a single source of truth also limits automation. Even when BIM or GIS tools are available, the absence of a normalized database structure makes it difficult to connect building objects, spatial data, design parameters, construction quantities, and documentation rules in a consistent way. Without a relational backbone, BIM data may remain isolated in modeling software, GIS data may remain isolated in spatial files, and estimation or structural data may remain locked in spreadsheets or calculation sheets. In the context of Nepal, this issue is more critical because building code implementation, seismic design requirements, municipal approval processes, and construction quality control require consistent and reliable information. Studies on building-code compliance and seismic vulnerability in Nepal indicate that safe construction practice depends not only on the existence of standards but also on their consistent implementation in design and construction workflows . Manual and fragmented information management makes this consistency difficult to achieve. Therefore, the problem addressed by this research is the absence of a normalized, integrated, and reusable database framework capable of connecting BIM, GIS, structural analysis, estimation, method statements, and specifications within a single AEC workflow. This research attempts to address the problem by designing and implementing a PostgreSQL/Supabase-based prototype in which shared project elements and dimensions are stored once and reused across multiple modules.

Research questions

Five questions structure the investigation

They progress from schema design and shared-data reuse to BIM/GIS framing, database-driven structural calculation and prototype validation.

  1. 01

    How can a normalized relational database schema be designed to manage shared AEC project information for building design and construction workflow automation?

  2. 02

    How can project elements, coordinates, dimensions, and parameters be stored as a single source of truth and reused across architecture, structural analysis, estimation, method statements, and specifications?

  3. 03

    How can BIM and GIS concepts be integrated with a relational database framework to support automated building design and site-based decision-making in the Nepalese construction context?

  4. 04

    How can a database-driven structural calculation module be implemented and traced within the same relational database environment?

  5. 05

    How can the developed prototype be validated in terms of data consistency, calculation traceability, quantity accuracy, and workflow integration potential?

Objectives

Design, implement, connect and evaluate

General objective

To design and implement a normalized relational database system integrating BIM and GIS concepts for automated building design and construction workflow automation in Nepal.

01

To design a normalized PostgreSQL/Supabase relational database schema for managing AEC project lifecycle data.

02

To develop a shared project element and dimension hub capable of storing building elements, coordinates, parameters, and units as reusable data.

03

To implement a database-driven structural analysis prototype using the Moment Distribution Method as a proof of structural calculation automation.

04

To demonstrate the reuse of shared element data for architectural line representation and concrete quantity estimation.

05

To link project elements with construction work items, method statement templates, and specification clauses.

06

To develop reporting and health-check views for validating calculation traceability, joint equilibrium, duplicate-data control, and workflow consistency.

07

To evaluate the prototype within the Pokhara-based Nepalese AEC context using consistency checks, quantity verification, and comparison with conventional manual workflow logic.

Methodology

Prototype-based database design and controlled validation

Prototype-based database design and implementation research using PostgreSQL/Supabase and a controlled two-span beam example.

  1. 01

    identification of the fragmentation problem in conventional AEC workflows

  2. 02

    definition of shared project data requirements

  3. 03

    design of normalized relational tables for project elements, points, parameters, loads, calculation steps, estimation rules, and documentation links

  4. 04

    implementation of the schema and calculation views in PostgreSQL/Supabase

  5. 05

    testing of the prototype using a sample two-span beam system

  6. 06

    generation of structural, architectural, estimation, and documentation outputs from the same shared data source

  7. 07

    validation of the results using query outputs, duplicate checks, convergence checks, and health-check views

Validation logic

What the prototype checks

Validation is deterministic and query-backed; it is not predictive model evaluation.

Validated

Data consistency

Shared dimensions and coordinates are reused across outputs instead of copied into disconnected files.

Validated

Calculation traceability

Exported MDM stages retain member, joint, end, value and unit context.

Validated

Health checks

Joint imbalance, duplicate stiffness locations, tolerance and convergence are evaluated in database views.

Validated

Quantity verification

Beam concrete volume follows the exported L × b × D rule for both members.

Scope of the test

The sample is a controlled two-span beam prototype. It was not tested as a complete real building project in Pokhara, and it does not establish production-scale performance.
